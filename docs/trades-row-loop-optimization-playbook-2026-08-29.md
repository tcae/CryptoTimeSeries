# Trades row-loop optimization playbook (2026-08-29)

Findings from optimizing `TradingStrategy.simulate_gains!` (the TrendDetector gain replay
loop). Written to be reused for the same exercise on `tradesim`, including `Trade` and `Xch`.

## 1. Result

`simulate_gains!`, 100k rows, single pair, measured with the frame built outside the timed
region:

| stage | µs/row | bytes/row |
|---|---|---|
| baseline | 28.2 | 39,040 |
| `_assert_hasfield` uses `hasproperty` + `_LANE_COLUMN` lookup table | 22.0 | 9,795 |
| `_RESETORDER_COLUMNS` (no runtime `Symbol` building) | 19.5 | 9,716 |
| `_LASTLANE_PREFIX` / `_STOPLANE_PREFIX` | 16.8 | 9,142 |
| `_tradescolumn` resolves the column once per accessor call | 13.8 | 7,200 |
| `TSM.TradesColumns` hoisted through `_rowtakeover!` | 9.8 | 4,895 |
| all 7 loop phases + `gain_limit_reversal!` on handles | 2.2 | 1,214 |
| function barrier on `cfg.algorithm` | **0.4** | **41** |

**~70x faster, ~950x less allocation. GC time went from 6% to 0.**

Isolated: `_rowtakeover!` went 5878 -> 109 ns/row and 2461 -> 0 bytes/row.

## 2. Causes, ranked by what they actually cost

Ordered by impact. The first three are API-layer overhead, **not** type instability — that
was the biggest surprise and the reason to measure before refactoring.

1. **Runtime `Symbol` construction** (~21% of self time). `Symbol(tradelane(label), "_", suffix)`
   in the TSM lane accessors interned a new symbol on *every cell access*.
   Fix: `const` lookup tables keyed by `(laneprefix, suffix)`.
2. **`field in propertynames(df)`** allocated a fresh 65-element `Vector{Symbol}` (576 bytes)
   on every accessor call. Fix: `hasproperty`, which hits the column index. 0 bytes.
3. **Per-cell `df[ix, :col]`**. Each access costs an index lookup, a `@boundscheck` that
   re-derives `nrow` through a dynamic dispatch, and — on writes — `_drop_all_nonnote_metadata!`.
   Fix: resolve the column once (`df[!, field]::Vector{T}`), then `@inbounds col[ix]`.
4. **Dynamic dispatch through an abstract field.** `StrategyConfig.algorithm::Function` is
   abstract, so `cfg.algorithm(cfg, cols, ix)` boxed **every argument**: 640 bytes/row, of
   which 544 was the 65-field `TradesColumns` struct. Fix: function barrier — resolve once,
   run the loop in a helper specialized on the concrete function type (`where {F}`).

### Why `nrow` is expensive
`nrow(df::DataFrame) = ncol(df) > 0 ? length(_columns(df)[1])::Int : 0`. `DataFrame` stores
**no row count**; it derives it from column 1 every time, and `_columns(df)` is
`Vector{AbstractVector}` so that `length` is a dynamic dispatch. It cannot be cached because
columns are aliasable (`copycols=false` shares caller vectors). Worse: `getindex(df, ix, col)`
calls `axes(df,1)` -> `size` -> `nrow` on **every read**.

### What did NOT matter
`Union{Missing,T}` does not allocate. `Vector{Union{Missing,DateTime}}` uses the small-union
optimization (unboxed elements + a parallel byte array of type selectors) and reads are
union-split. I guessed this was the culprit and was wrong — don't chase it.

## 3. Measured comparison of access strategies

`_rowtakeover!`, 31 carried fields, 200k rows. All variants verified to produce
byte-identical DataFrames before timing.

| variant | ns/row | bytes/row | speedup |
|---|---|---|---|
| label-based lane accessors (`settrades_limit!(df, ix, label, v)`) | 5878 | 2461 | 1.00x |
| per-field accessors (`settrades_lo_limit!(df, ix, v)`) | 3644 | 2349 | 1.61x |
| direct `df[ix, :col] = df[ix-1, :col]` | 3040 | 3020 | 1.93x |
| **hoisted column vectors** | **402** | **511** | **14.6x** |
| hoisted + categorical ref-array copy | 449 | 255 | 13.1x |

Two conclusions:
- Raw DataFrame indexing is **not** the fix. It is only 1.9x and it *allocates more* than the
  accessors (metadata drop per write + boxed reads).
- Reaching past `CategoricalArray` to its `refs` buys no time (there is already a same-pool
  fast path for `col[ix] = col[ix-1]`) and is not worth breaking the abstraction.

**Rule of thumb:** keep the `TSM.settrades_*!` accessors for boundary and occasional row
updates — schema ownership, categorical level management, validation. Never use them
per-cell inside a row loop.

## 4. The mechanism: `TSM.TradesColumns`

65 typed column handles. Struct and constructor generated by `@eval` over
`const TSM_TRADES_COLUMNS` (which also drives the per-field accessors, so schema and handles
cannot drift) plus `tradescolumntype(field)`.

- concrete type, **0 bytes to construct**, aliases the DataFrame columns so writes pass through
- `TSM.setcategorical!(col, ix, value)` is the handle-based counterpart for categorical writes
- docstrings must live **inside** `@eval begin ... end`; attaching one to a top-level `@eval`
  fails with "cannot document the following expression"

### Handle validity — critical for tradesim
- handles **survive `push!`** (the `Vector` object identity is stable when it grows)
- handles do **not** survive whole-column replacement (`df[!, :col] = newvec`)
- **`TSM._inserttradesrow!` replaces the entire DataFrame** in `pairstates`, and `settrades!`
  does too. Any held `TradesColumns` is stale afterwards.
- `_ensurecolumn!` replaces columns during schema normalization, so build handles **after**
  the schema is applied

Replay is safe because the frame is prepopulated and never structurally changed mid-loop.
**tradesim appends rows as it goes**, so this is the main hazard for the next exercise:
either rebuild handles after any structural change, or prove none happens in the loop.

## 5. How to repeat the exercise

Reusable harnesses (templates, adapt the builder and the phase list):

| script | purpose |
|---|---|
| `~/crypto/debug/profile_simulate_gains.jl` | totals + per-phase time/alloc breakdown + flat sampling profile |
| `~/crypto/debug/bench_rowtakeover.jl` | compare access strategies on one hot function, with an equality check |
| `~/crypto/debug/alloc_gain_limit_reversal.jl` | `Profile.Allocs` by allocated **type** and source line |
| `~/crypto/debug/alias_writeback_demo.jl` | show which write patterns propagate through an aliased column |

Sequence that worked:
1. Build a synthetic single-pair driver so runs are seconds, not minutes.
2. Instrument the loop with `@timed` per phase to get a time **and** allocation split.
3. Flat sampling profile (`Profile.print(format=:flat, sortedby=:count)`) for self cost.
4. Use `Profile.Allocs` to attribute the remaining allocation **by type** — this is what
   identified the boxed `TradesColumns`, which no timing view would have shown.
5. Fix the cheapest/highest-ratio item, re-measure, repeat.

### Measurement traps I fell into
- **`wall` included frame construction.** Negligible at 28 µs/row, dominant at 0.4. Build the
  frame outside the timed region or the number becomes meaningless.
- **The harness must mirror production.** Mine called `cfg.algorithm` directly while production
  called it behind a barrier, so it kept reporting 640 B/row that production no longer had.
- **Constant probe values hide bugs.** My first carry test used `scores = fill(1f0, n)`, so a
  wrongly-added score carry was invisible. Give every cell a unique value per (column, row).
- **Passing tests prove nothing about an untested path.** The `SubDataFrame` bug (§7) survived
  a green suite because no test ever passed a `SubDataFrame`.

### Grep list for the next module

## 6. Guard the behaviour before refactoring

`_rowtakeover!` carries 29 of 65 fields and leaves the rest alone — it is **not** a blind copy.
Before porting it I wrote `TradingStrategy/test/rowtakeover_carry_test.jl` (142 tests): explicit
carried/untouched partition, prepopulated-columns-never-written, `ix == 1` no-op, a 400-row
sequential diff against an independent reference implementation, and a set-disjointness check.

**Mutation-verify every pin.** I checked an extra carry, a dropped carry and a score carry.
The third one initially passed — which is how I found the constant-probe weakness above.

Do the same for `tradesim`: pin the per-minute state transition against a reference before
touching it, and prove the pin fails when the implementation is perturbed.

## 7. Schema enforcement — the bug class this exposed

The `TradesColumns` type asserts surfaced four **pre-existing, silent** violations. TSM
declared a schema but did not enforce it on frames adopted from elsewhere.

| violation | origin | consequence before |
|---|---|---|
| `:pair` a plain `Vector{String}` | `_ensuretradesidentity!` overwrote the categorical | schema lie, invisible |
| `SubArray` columns | `groupby` view adopted with `copycols=false` | **replay wrote `:label` and truth-pass `:score` back into the shared predictions table** |
| `rangeid` as `UInt16` | `EnvConfig._arrow_safe_table` compacts every integer column on write | schema lie, invisible |
| `:set` a `CategoricalVector{Union{Missing,String}, UInt32, ...}` | `Classify` `allowmissing!` + Arrow dictionary encoding (always `UInt32` refs) | schema lie, invisible |

All four are now normalized in `TSM._ensurecolumn!` (categorical via `_canonicalcategorical`,
int -> `Int32`, float -> `Float32`), plus `TSM._assert_owned_columns` in both `settrades!`
methods to reject view-backed frames at the store rather than at some unrelated setter
downstream.

**If a new `expected X, got Y at _tradescolumn` appears, it is this class.** Fix it by
normalizing in `_ensurecolumn!` — do not loosen `TradesColumns`.

### Categorical columns need two normalizations, not one

A foreign pool differs from the schema on two independent axes, and both must be rebuilt:

- **eltype** — `allowmissing!` leaves `Union{Missing,String}`, which changes the
  `CategoricalVector` type parameters even when no cell is actually missing.
- **reference width** — `compress=true` yields `UInt8`, Arrow dictionary encoding always
  yields `UInt32`. A round-trip silently widens every categorical column.

`_canonicalcategorical` rebuilds both and asserts the level count fits the target reftype,
which makes the 255-level `UInt8` ceiling on the `*_msg` columns a hard failure instead of
a silent overflow. Producers writing free-form text there (`XchCore.jl` writes
`String(ev.reason)`, `Trade.jl` writes formatted issue text) will now trip it.

An unset cell — `push!(df, row; cols=:subset)` leaves `missing` — materializes to
`TSM_CATEGORICAL_DEFAULT`. That is schema materialization, not a fallback: it is the same
value `_defaultcolumn` writes for a fresh column, and `settrades_ownership_test.jl` pins
that every categorical column agrees on that default so the shared constant stays valid.
Only `_appendtradesrow!` pushes rows in production and it always builds a complete row, so
subset pushes are a test-side idiom.

Note on the aliasing case: only writes sourced from a *fresh* array propagate back.
`x .= same_view` is a no-op, which is why `close`/`high`/`low` were never corrupted while
`:label` and truth-pass `:score` were.

## 8. Open items

- **255-level cap on compressed categoricals.** `*_msg`, `:config`, `:set`, `:tsmstate` use
  `compress=true` -> `UInt8` refs. `_ensurecategoricallevel!` aborts past 255 levels and the
  pool never shrinks. `:tsmstate`/`:set`/`:config` are bounded, but `*_msg` is **not**:
  `XchCore.jl:1673` writes `String(ev.reason)` and `Trade.jl:551` writes formatted issue text.
  A long `tradereal`/`tradesim` run will hit this. Decide: widen those columns to `UInt32`,
  or normalize/cap message text at the write site.
- **Residual 41 bytes/row** in `simulate_gains!`: 31 from the `NamedTuple` returned by
  `_open_hit_spec`, 10 from the gain `push!`. Both are doing real work.
- **`lastrow`/`newrow` struct port** was considered and deferred. Measured benefit over hoisted
  columns is small; its real value would be unifying the live-append and replay-mutate paths.

## 9. Applying this to tradesim / Trade / Xch

- The per-cell cost is identical — `Trade` and `Xch` use the same `TSM.settrades_*!` accessors
  (~27 `settrades_msg!` call sites alone), so items 1-3 of §2 apply unchanged and are already
  fixed by the TSM-level changes.
- The **live** path is one row per minute, so per-row cost is irrelevant there. The target is
  the tradesim simulation loop, which runs the same code over historical minutes at speed.
- Expect the handle-validity hazard (§4) to be the main structural difference: tradesim appends
  rows via `ensuretradesrow!`, and `_inserttradesrow!` replaces the frame outright.
- Check `Trade`/`Xch` for the same abstract-field dispatch pattern as `StrategyConfig.algorithm`
  before assuming the cost is in the row logic.
- Expect more schema violations (§7) as soon as typed handles are introduced there — each one
  is a pre-existing silent bug, not a regression.
